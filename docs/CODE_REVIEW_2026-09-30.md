## 1. [P1] 多金额通知会把优惠或余额记成支出

**位置：** [NotificationListener.kt:32–34](../android/app/src/main/kotlin/com/finance/flutter_finance/NotificationListener.kt)。

解析器在正文任意位置寻找第一个“货币符号 + 数字”或“支付成功等关键词 + 数字”。前面的成功关键词检查只证明正文某处出现成功文案，并没有将金额绑定到实际付款字段。因此同一通知包含优惠、余额和实付时，会选错金额并写入数据库。

**复现输入与实际结果：**

| 正文（假设来源、标题满足现有过滤） | 当前提取值 | 应关注的实付金额 |
| --- | --- | --- |
| 支付成功 ￥20.00 商户：测试店 | 20.00 | 20.00 |
| 优惠￥5.00，支付成功￥95.00，商户：测试店 | 5.00 | 95.00 |
| 余额￥900.00，支付成功￥100.00，商户：测试店 | 900.00 | 100.00 |

**验证：** 从 Kotlin 源码直接抽取正则，在 Java 的 `java.util.regex.Pattern` 中执行上述三个合成样本，输出与表一致。Kotlin/JVM Regex 使用同类 Java 正则语义；这验证了金额选择逻辑，但不是 Android 真机通知测试，样本不是声称采集到的真实支付文案。

**影响：** 错误金额进入流水和全部汇总；现有 UI 不能修改或删除记录。

**建议：** 按来源及明确的通知模板绑定实付字段；遇到多金额歧义时不要静默取首个金额。用脱敏真实样本覆盖实付/优惠/余额共存、千分位、小数、退款和不支持格式。

## 2. [P2] 通知更新时间参与事件 ID，无法去重同一笔更新通知

**位置：** [NotificationListener.kt:39–42](../android/app/src/main/kotlin/com/finance/flutter_finance/NotificationListener.kt)；相关逻辑见 [database_helper.dart](../lib/database/database_helper.dart) 的 `insertTransaction`。

事件 ID 是 `sbn.key + ":" + sbn.postTime`。当同一笔支付的通知以同一个 key 更新、重新发布时间发生变化时，会形成不同 ID；数据库只按 event_id 判重，因此两次都入账。持久化队列与写库后确认机制能防止“同一 ID 的重放”，但不能防止这一种通知更新重复。

**触发条件：** 同一笔支付产生两个符合过滤规则的回调，key 相同、postTime 不同。是否以及多频繁出现，需要对各版本微信/支付宝真机采样确认。

**逻辑示例：** `payment-key:1000` 与 `payment-key:2000` 会被视为独立记录，即使商户和金额完全一致。现有数据库测试明确验证了不同 eventId 会保留两条，因此它不能验证真实订单级去重。

**建议：** 优先使用能从可信模板提取的稳定订单标识；若不可得，需要定义通知生命周期及保守的重复候选策略。不能简单只用 key，也不能简单按商户+金额永久去重，因为通知 ID 可能复用、相同金额也可能是真实的连续支付。应增加“同一通知更新”和“同额的两笔真实支付”的成对测试。

## 3. [P2] 分类饼图没有类别标签或图例

**位置：** [expense_pie_chart.dart:30–34](../lib/widgets/expense_pie_chart.dart)；调用页面为 [reports_screen.dart](../lib/screens/reports_screen.dart)。

扇区标题仅为百分比，父页面也没有提供类别图例、金额明细或自定义类别提示。用户进入“本月支出分类”后，只能看到颜色和百分比，无法在当前页面确定某个扇区属于哪类支出；只有去设置页记住分类颜色才能间接推断。

**复现条件：** 当月存在两个或更多不同类别的支出时查看报表。

**建议：** 在图表旁增加“颜色、类别、金额、百分比”图例或可访问的明细列表，避免只靠颜色传达类别。可增加组件测试，确认传入两个类别后页面可找到它们的名字与金额。

## 其他待验证点与功能边界

以下单独列为边界或待验证风险，不计入上述 3 个已定位问题：

- 包名与标题白名单不是支付来源真实性证明。微信聊天通知可能有可控标题；应使用真实通知的 channel/category/模板等信息区分聊天与支付，并验证同名联系人的误识别场景。本轮未拿到这类真机样本，不声称已复现真实误入账。
- 暂存队列整批解析与 Dart 导入采用外层异常捕获；异常数据的隔离与后续记录继续导入缺少专门测试。当前生产者生成的数据通常满足格式，尚未验证真实坏数据路径。
- UI 没有手动补账、编辑、删除、导出或恢复。数据库虽然提供 update/delete 方法，但不等于用户能操作；本轮指南据此明确了漏记/错记的限制。
- AI 分类结果会生成持久化的商户规则，关闭 AI 不会清除规则。商户名包含匹配可能扩大规则作用范围，分类质量需要进一步实测。
- 平台目录存在不代表平台已支持；生产入口没有桌面/Web 数据库工厂配置，通知采集只有 Android 原生实现。
- 原有 README/部署文档记载的“16 项测试通过”是既有记录，本轮未复验；旧部署文档中“目录尚未初始化 Git”的描述也不再符合当前已上传仓库的状态。

## 已有实现中确认的保护措施

- 数据库写入校验有限正金额，查询参数化；同 event_id 的重放有事务和唯一索引保护。
- 原生通知在 Flutter 不运行时可先写入持久化队列；数据库写入完成后再确认移除。
- 页面使用加载版本号避免旧请求覆盖新筛选结果；失败时提供重试。
- 分类先查本地规则；AI 输出限制为预设类别，失败时回退；API Key 只保存在会话内存。
- 月份查询使用右侧开区间，日均按自然日计算，图表对空值/零值作了处理。
